# Energy Central Partner Portal

Client-facing portal replacing the per-client "Customer Report" Google Sheets. Clients log in and see their own
campaign results and leads; the EC team uses `/admin` to review numbers before clients see them.

## Stack
- Next.js 16 (App Router, `src/`), Tailwind v4, deployed on Vercel. **Read `AGENTS.md` first: this Next version differs from older docs** (`proxy.ts` not middleware, async `params`, Cache Components on; root layout sets `instant = false` because every page reads the session).
- Supabase project "EC Client Portals": Postgres + Auth (email/password). Schema in `supabase/migrations`, seeds in `supabase/seed` (already applied).
- Data pulls are TypeScript scripts in `scripts/`, run with the service role key. They log every run to `sync_runs`.

## Rules that must hold
- **Row-level security is the access control.** Clients read only their own `client_id` rows, and only `metrics` with `status = 'approved'`. Never query with the service role key from app code; only `scripts/` uses it. One exception (Chloe, Nov 12 2026, for the Logins screen): `src/lib/supabase/admin.ts` uses it for Supabase `auth.admin` calls only (make a login, make a one-time link, block a login), from `/admin/logins` actions after the caller is checked to be an admin. Never read or write tables with it.
- **No public sign-up.** Logins are made in `/admin/logins` ("Logins"): a Team section (role `admin`) and client logins grouped by client (`?client=<slug>` for one client; each client page has a Logins tab). Adding never sends an email (Chloe: do not invite anyone) and nothing expires (Chloe, Nov 12 2026: "for clients we cant have a time expiration we need to give them logins"): `auth.admin.createUser` makes the login with a password generated in the action and shown once, for the admin to pass on with the email. "New password" on a row replaces it. Anyone signed in can change their own at `/login/password` ("Change password" in the header). The sign-in pages share `LoginFrame` (logo on navy, "Client Portal"; Chloe's name for it). Remove = `profiles.removed_at` set, role/client stripped, sign-in blocked (ban); the row is kept because approvals point at it; `is_admin()`, `my_client_id()` and `getProfile()` ignore removed profiles. Needs `SUPABASE_SERVICE_ROLE_KEY` in Vercel.
- **Numbers reach clients only after approval** in `/admin/approvals`, except figures from a client's old report, which arrive approved (see task 9). Pull jobs insert `pending`, or `flagged` with a `flag_reason` when a value is far outside that client's usual range.

## Metric definitions and timing (from Isuri's "EC SOP Production" doc)
| Deliverable | Numbers | Source | Pull when |
|---|---|---|---|
| Newsletter ad | impressions = Total Opens of that day's EC Daily; clicks | beehiiv; short.io | 14 days after run date |
| Email blast | sent = Delivered, opens = total opens, clicks = total raw clicks (SOP says unique; the sheets and the portal use totals, see below) | beehiiv (EC Marketing pub) | 7 days after send |
| Webinar / PowerSession | registrants, attendees; live leads | Zoom Events | day after; on-demand leads flow in continuously from Tally |
| Podcast | plays (Flightcast, no API: manual), short_form_views (YouTube + LinkedIn), impressions, clicks | mixed | 30 days after publish |
| Content | views, likes, comments | Bettermode (beehiiv after migration) | 14 days |

Short.io links do not follow one naming pattern (`Semtech.10.8.news`, `Semtec.9.10.news`, `Semtechnews2.22`), so never derive a link from client+date: store it on the deliverable (`short_link`). Clicks = short.io human clicks, all time, read once the ad is 14+ days old and then never re-read (this is what the old sheets used; short.io's custom date window undercounts against them). Bot farms are handled by the outlier rule in `pull-beehiiv.ts`.

## Creative approvals (PJ's ask, Nov 11 2026)
Called "Creative approvals" everywhere a person reads it (Chloe); `proofs` is only the table and code name.
The team adds the creative a client must sign off (`proofs` table, files in the private `proofs` storage bucket under `<client_id>/`); the client approves or requests changes in the portal through the `review_proof` function, which is the only write clients have. A proof is tied to the placement it runs in (`deliverable_id`); a newer proof for the same placement is the next version and older ones fold away. Each proof can carry the ad copy and the click-through URL, and an approve-by date (default 3 days before the run date). Newsletter creative is previewed the way it runs in the Daily (`NewsletterPreview` in `Proofs.tsx`: image beside copy between two rules, or the "Today's edition is sponsored by" logo for Hero); `proofs.format` overrides the layout and `cta_text` is the linked phrase. The placement picker lists open inventory only (Notion status Not Started, Awaiting assets, Ready for production, Production in progress, Scheduled, On hold). Adding creative emails the client's logins when the box is ticked and `RESEND_API_KEY` + `PORTAL_FROM_EMAIL` are set in Vercel (not set yet); the form always says who was or was not emailed. The team is not yet notified when a client responds.

## Leads
- **Lead rows are personal data: never commit them to the repo** (no `data/*.json` for leads, unlike metrics). Semtech's history was loaded straight from the lead sheets into Supabase through the SQL editor.
- `leads.source` + `leads.attended` drive the client-facing "how they came in": `webinar_live` + attended → "Attended live", `webinar_live` + not attended → "Registered", `webinar_on_demand` → "Watched on demand". `leads.origin` records the system (zoom, tally, legacy_sheet, manual).
- Leads have no approval step: clients see them as soon as they land.
- **One person per session** (Chloe, Nov 13 2026: "keep them once but make it clear they downloaded both"). The database keeps one row per sign-up (Zoom registration, Tally on-demand form); the client view merges rows with the same email on the same placement into one lead whose "how they came in" lists both ("Registered" + "Watched on demand"), in the table, the filter and the CSV. The Leads total and each session's lead count count that person once.
- **Leads table filters** (Chloe, Nov 12 2026, replacing the "Who you reached" section): type of organization as chips with Utilities highlighted in yellow (a Utility badge on rows; the "X% work at utilities" line was removed at Chloe's ask), then seniority, company, how they came in and source. Type and seniority are guessed from company name and job title in `src/lib/leadProfile.ts` (utility name list + keywords); the page says a few will be off. Both go in the CSV.

## Where the data lives, and backups (Chloe, Nov 13 2026: "how do I make sure we have backups", "that doesn't magically get deleted")
- Everything that exists only in the portal (approvals, typed-in results, leads from Zoom and Tally, logins, creative and client sign-offs) is in the Supabase project, which was on the **Free plan with no backups** when checked on Nov 13 2026. Upgrading to Pro (daily backups, 7 days) is Chloe's to do. Results from old reports are also in `data/legacy` in the repo; sold/scheduled inventory is in Notion; the original reports and lead lists are in Drive.
- **Backups screen** (`/admin/backup`, in the menu under the email): "Download full backup" (`/admin/backup/download`, every table as one Excel workbook, run as the signed-in admin) and the state of the weekly copy.
- **Download everything** on a client's Team and Client views (`/admin/clients/<slug>/export`): one Excel file, all years: placements with every result, leads, creative approvals, campaigns. It is the team's copy (it marks results still waiting and has internal campaign names).
- **Weekly copy to Drive**: `scripts/backup.ts` ("Weekly backup to Google Drive" Action, Sundays 3:23am ET) writes a dated .xlsx and a lossless .json.gz to a Drive folder. It needs secrets `GOOGLE_SERVICE_ACCOUNT_JSON` and `BACKUP_DRIVE_FOLDER_ID` (a folder in a shared drive, or shared with the service account as Content manager); until both exist the scheduled run does nothing. Backups hold lead rows, so they go to Drive only: never the repo, never GitHub artifacts. Creative files in Supabase storage are not copied yet.
- Nothing deletes on its own: pulls only add or update, rejected/retired results keep their row, removed logins are kept and blocked. The only delete button is "Delete this for good" on a creative. Deleting a client row in Supabase cascades to everything under it; never do it without moving the rows first (as with LocusView → Itron).
